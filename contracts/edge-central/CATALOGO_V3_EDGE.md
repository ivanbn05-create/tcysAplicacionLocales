# Candidato de publicación de catálogo v3 para Central ↔ Edge

Autoridad funcional: `docs/autoridad/ESPECIFICACION_PRODUCTION_1_0_LOS_TOCAYOS.md` y decisión de catálogo inicial de Arboledas. Este contrato es **candidato hasta conciliación con agente1**; las rutas de Central siguen apagadas. No contiene datos reales de Arboledas. El fixture `fixtures/catalogo-publicacion-v3-lab01-promocion.json` es sintético.

- Esquema: `schemas/catalogo-publicacion-v3.schema.json`.
- Sobre exacto: `version_contrato=3`, `tipo=snapshot_completo`, `release_id`, `publicacion_id`, `publicacion_anterior_id`, `version_sucursal`, `sucursal:{id,clave}`, `publicada_en`, `aplicar_desde`, `moneda=MXN`, `conteos:{categorias,productos,promociones}`, `contenido:{categorias,productos,promociones}`, `contenido_sha256`.
- Categoría: `{categoria_central_id,codigo,nombre,orden,activa}`.
- Producto: `{producto_central_id,categoria_central_id,codigo,nombre,nombre_corto,orden,permite_termino,termino_predeterminado,abreviaturas_termino,destino_impresion,activo,disponible_sucursal,imagen,precio}`. `imagen={politica:"conservar_local_o_placeholder",asset:null}`; `precio={importe,origen,vigente_desde,vigente_hasta}`.
- Promoción: `{id,codigo,nombre,producto_central_id,precio,activo,dias_semana,fecha_desde,fecha_hasta,grupos}`. Grupo: `{id,nombre,orden,cantidad,productos_permitidos}`. Los permitidos son UUID de producto maestro. `codigo` y `precio` de la promoción igualan al producto principal publicado.
- Días ISO de Python: 0 lunes ... 6 domingo; fechas inclusivas o nulas, sin horario. Elegir promoción es una acción explícita del POS.
- Tamaño del JSON canonizado ≤1 MiB. Límites: 1..500 categorías, 1..5000 productos, 0..500 promociones, 1..16 grupos por promoción y 1..500 productos permitidos por grupo. `contenido_sha256` es SHA-256 sobre JSON UTF-8 de `contenido` con claves ordenadas, sin espacios y `ensure_ascii=False`.
- Primera publicación: `version_sucursal=1`, predecesora `null`; siguientes versiones enteras consecutivas y `publicacion_anterior_id` igual a la aplicada. Un Edge que ya aplicó v3 rechaza volver a v2. v2 sigue legible temporalmente para migración, pero no habilita una nueva instalación 1.0.
- `activo && disponible_sucursal` determina venta local. El Edge conserva mapeos/histórico de productos retirados, desactiva su precio actual y bloquea API directa. Un producto vendible requiere además precio local idéntico al snapshot y `publicacion_central_id` actual. No se infiere ningún mapping por nombre.
- Aplicación de categorías, productos, precios, promociones, estado de aprovisionamiento y ACK outbox ocurre en una transacción SQLite. Snapshot inválido, checksum incorrecto o error tardío revierten toda la publicación y dejan la última válida. Una publicación válida nueva no recalcula partidas históricas.
- Estados locales durables: `enrolado` → `esperando_catalogo_inicial` → `catalogo_aplicado` → `listo`; el último paso exige confirmación operativa explícita externa (dueño, impresión, respaldo). Salud HTTP técnica no equivale a listo.

**Rutas por conciliar con Central:** el cliente actual descarga por `GET /api/v2/edge/catalogo/publicaciones/actual/` y envía ACK v2 por `POST /api/v2/edge/catalogo/publicaciones/{publicacion_id}/acuse/`. Agente1 debe decidir si v3 exige rutas y scopes nuevos; Edge ajustará el cliente una vez congelado el contrato. El import del catálogo vigente real de Arboledas a Central y la publicación inicial de cada sucursal son pendientes. No activar `CENTRAL_ENABLE_CATALOG_DISTRIBUTION_V2` ni instalar esta candidata hasta E2E Central/Edge y corte autorizado.
